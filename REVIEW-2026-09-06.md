## 4. Database design and SQL (the parked items are answered here)

Measured on the rebuilt 928,935-resource MIMIC load, 2026-09-06
(`packages/fhirant_server/tool/review_2026-09-06/index_ab.dart`, results in
`index_ab.tsv` beside it): §4.5.

### 4.1 Every WHERE carries a dead OR

Every condition is written `resource_type = ? AND (search_name = ? OR
search_path LIKE 'T.name' OR search_path LIKE 'T.%.name') AND value …`. The
two LIKE alternatives exist for rows written before schema 5 carried
`search_name`. The generated extractor passes `searchName` on all 1,802 of its
1,802 calls, and schema 7 rebuilt every row from the stored resources, so no
row without one exists. The OR cannot use an index on `search_name` and it
forces a string LIKE per candidate row. Drop it: `resource_type = ? AND
search_name = ? AND value …`. This is the precondition for everything below.

### 4.2 The value indexes do not serve string searches at all

MEASURED (plan, `probes/OUTPUT.txt`): the default string search
`string_value LIKE 'family1%'` plans as `SEARCH … USING INDEX
sqlite_autoindex_string_search_parameters_1 (resource_type=?)`, that is, every
string row of the resource type is read and the LIKE evaluated on each.
SQLite's LIKE optimization needs `PRAGMA case_sensitive_like` or a `NOCASE`
column; neither is set (`PRAGMA case_sensitive_like` returns no row; nothing in
either repo sets it). The same query as a range, `string_value >= 'family1'
AND string_value < 'family2'`, uses `idx_string_value`. Token `:text`
(`substr(token_display,1,n) = ?`) and string `:contains` (`LIKE '%x%'`) can
never use an index by construction. The values are already lower-cased and
folded, so a range is exact for starts-with; `:contains` is a genuine scan
and should be documented as one.

### 4.3 The resources table has no time index

MEASURED (plan): `ORDER BY last_updated DESC LIMIT 20` is `SCAN resources |
USE TEMP B-TREE FOR ORDER BY`, so `GET /Observation` with no parameters sorts
every Observation for each page. `_lastUpdated`, `_since` on history, export
and compartment members all scan. One index `(resource_type, last_updated)`.

### 4.4 The key (parked item 2) and the composite indexes (parked item 1)

Today each index table is a rowid table whose declared PK
`(resource_type, id, search_path, search_name, param_index)` is a separate
unique index, plus single-column value indexes. `search_path` (a FHIRPath
string, 20–60 bytes) is stored in every row and every PK entry and, after
§4.1, is never queried. The shape that serves the actual queries:

- rowid table; columns `resource_type, id, search_name, param_index, value…`
  (drop `search_path`, or keep it out of every index);
- one owner index `(resource_type, id)` for the delete-before-reindex;
- one composite covering index per table with the value **and the id**:
  `(resource_type, search_name, token_value, id)`,
  `(resource_type, search_name, date_value, id)`,
  `(resource_type, search_name, reference_resource_type, reference_id_part, id)`,
  `(resource_type, search_name, string_value, id)`, and so on.

A covering composite lets a single-parameter search answer from the index
alone, lets a sort walk the index in order, and removes the per-row PK probe.
It replaces, not adds to, the current single-column indexes (measured in §4.5:
+703 MB if simply added; a net reduction once `search_path` leaves the key and
the single-column indexes go). Parked item 4
(delete-then-insert on re-index) stands as answered: correct, keep it.

What this settles:

- **Parked item 1 (the 8.9 s sort).** The grouped-join shape cannot be
  rescued by indexes; it sorts the whole filtered set. The answer is the
  index walk **when the filter keeps most of the type** (0 ms) and the
  filtered-set sort **when it does not** (0.19–0.34 s for 48k rows, 6–9 ms
  for 963). The DAO already probes every part's size to choose the outer
  select; the same numbers choose between the two sort shapes. The earlier
  attempt at a walk was 13× worse because it had no covering index to walk
  and the 48k patient is exactly the case that must take the other shape.
- **Every plain search benefits** once the LIKE ORs go: token 100 ms → ≤6 ms
  from the covering index alone, and DISTINCT no longer needs a temp B-tree.
- **`GET /[type]` and every `_since`/`_lastUpdated` go from ~6 s to 0** with
  one 26 MB index.
- **Parked item 2 (the key), by `dbstat` on this load.** Data 1.07 GB
  (`resources`) and **1.07 GB again in `resources_history`**, which holds a
  full copy of every current version. The nine index tables total 2.05 GB of
  rows plus **1.16 GB of PK autoindexes** (the five-column key with
  `search_path` in every entry) plus 0.74 GB of single-column value indexes.
  The five covering indexes cost **+703 MB** on top of today's layout; with
  `search_path` out of the key and the single-column value indexes dropped
  (they are subsumed), the layout is smaller than today's, not larger.
  Largest objects: token rows 613 MB, reference rows 608 MB, token PK 367 MB,
  reference PK 335 MB, composite rows 316 MB, `idx_token_system` 241 MB (a
  single-column index nothing seeks on alone).
- **Not parked, found by `dbstat`:** history duplicates the current version.
  17% of the file is a second copy of every resource. Either store only
  superseded versions in history and read the current one from `resources`,
  or the reverse.


### 4.6 Other DAO points

- `rebuildSearchIndex` pages with `LIMIT/OFFSET` over the PK, a quadratic walk;
  keyset pagination (`WHERE (resource_type, id) > (?, ?)`).
- Page hydration is 20 single-row `getResource` calls; one `id IN (…)` then
  reorder.
- `_getCodesFromValueSet` recurses into `search()`; fine, but see finding 24.
- The three db packages are hand-kept copies (r4 vs r5 DAO differ in 75 of
  4,406 lines, all version names). The DAO reads nothing version-specific but
  the generated tables of definitions; it should be one model-independent
  package over `FhirNode`, the shape `fhir_path` and `cql` already have, with
  the generated per-version data plugged in. Every finding in §2–§3 lands
  three times until then.
- The `canonical_resources` table exists in the schema and is unused by
  fhirant: spec canonicals (StructureDefinitions, ValueSets, CodeSystems,
  ~48 MB of NDJSON on the CLI) are loaded into `resources`, so they are
  exported by `$export`, dumped by `$backup`, listed by `_history`, counted
  on the dashboard, and resolved by `DbResourceCache` with five type searches
  per canonical. The keyed table is the right home and makes resolution one
  PK read.

What the three columns say:

- **Schema 10 alone** takes every equality search to the covering index: a patient's Observations 370 → 15 ms, their count 441 → 13 ms, a token page 172 → 9 ms, the compartment 393 → 33 ms, the two-parameter AND 504 → 131 ms, the sorted searches to 40–45 % of their time. Plans in the TSV (`2-plan`): `COVERING INDEX idx_*_cover`, `idx_resources_type_updated`, the owner index for the delete.
- **Two regressions surfaced by the same run**, both in how a single parameter's page was cut. `SELECT DISTINCT id … ORDER BY id LIMIT 20` left the choice to the planner: a broad range through the new covering index came out in value order and was sorted whole in a temporary B-tree (`date=ge2150`, 25 → 764 ms), and a sparse `_lastUpdated` was read in key order testing every row (10.4 s to return nothing; it was written as an OR of two ranges no index could serve). The page-shape commit: `_lastUpdated` is one range per prefix; a single RANGE parameter (date, `_lastUpdated`, string starts-with) is sized by the probe and either fetched whole through its index and paged in Dart (under 100,000 ids) or found by walking the resources table in id order with the part as an EXISTS probe (at or above); an EQUALITY parameter keeps the SQL page, because its covering index already yields id order and stops at the page (measured on the way: fetching the 48,554-record patient whole cost 600 ms against 15). Number and quantity prefixes are ORs over low/high with NULL bounds that no single range serves, so they keep the SQL page too (`value-quantity=gt100` through the probe measured 1.2 s; a sargable numeric range is a follow-up). A `count(*)` of the type that had guarded only multi-parameter searches was briefly on every single-parameter one (~100 ms on 929k) and is guarded again.
- **The fourth column, the sort walk.** For one sort key the first 200 rows of the key's index in sort order are read with the filter as a column; a quarter or more passing chooses a walk of that index with EXISTS probes (earliest row per resource by NOT EXISTS, the no-value tail appended from `resources` on the last pages), otherwise the grouped join. `status=final&_sort=-date` 1,004 → 33 ms warm (251 cold); the two patient sorts stay on the join, as they should (§4.5: the big patient's records sit in one band of dates and a walk read most of the type). A first version decided by a type count plus a probe to half the type and cost ~200 ms per query for the same answer (`sort-walk` in the TSV, 255 ms); the sample costs 200 index rows.
- **The third column carries a floor shift of ~20 ms** on rows whose code path did not change (the type page 17 → 34, `:exact` 1 → 2, `_id` 1 → 7): the copy had been through three rebuilds and an index drop-and-recreate by then. `hydration_probe.tsv` puts the id page of `subject=<big>` at 0–1 ms and the 20 single-row reads that hydrate it at 30–50 ms cold, 2–4 ms as one `IN (…)`: the hydration (§4.6) is now the larger part of an equality search.
- **Sizes (dbstat, `3-dbstat`).** Rows: token 535 MB (was 613), reference 505 (608), composite 301 (316). Indexes: the sixteen covers 2.16 GB and the nine owner indexes 0.63 GB, against 1.16 GB of key indexes plus 0.74 GB of single-column indexes before, so the index layout is **0.9 GB larger**, not smaller as §4.5 expected; the two on long strings dominate (token_system 437 MB, reference_value 334 MB). `index_trim_ab.dart` dropped those two and timed what they serve: a `system|` search with no match went from 2 ms to **1.15–1.19 s** and an absolute-reference search from 0 to **1.0 s** (matching ones stayed at 30–60 ms, they stop early). They stay. The file did not shrink (6.95 GB before and after): SQLite returns freed pages to the free list, not the file; `VACUUM` (or the `VACUUM INTO` backup of §5) reclaims them.
- **The rebuild** ran 1,022 s for 8 → 9 and 993 s for 9 → 10: `rebuildSearchIndex` pages with `LIMIT/OFFSET` over the primary key (§4.6), so each page walks the ones before it. Keyset pagination is the hygiene item that fixes it.

### 5.1 `$backup` as an encrypted SQLite file (2026-09-07)

`FhirAntDb.copyEncrypted(path, passphrase)`: `ATTACH DATABASE path AS bk KEY passphrase`, every table and index of `sqlite_master` recreated in `bk` and filled with `INSERT INTO bk.t SELECT * FROM main.t`, `user_version` carried across, streamed by SQLite. `VACUUM INTO` was measured first (`tool/review_2026-09-06/vacuum_probe.dart`) and rejected: under sqlite3mc the copy keeps the SOURCE key, which is the device key that cannot travel. Whole 6.98 GB MIMIC store (928,935 resources, 12.6 M rows) with its indexes: 215 s, half of it the index builds, the table copies holding 226 MB resident and the index builds taking the process to 707 MB (`attach_copy_probe.dart`, `attach_copy_rss.tsv`). So the copy carries no indexes: the restore reads tables only, and a backup opened as a database gets them from `createValueIndexes`. Tables only, through `BackupService.createFile`: **41 s, a 4.08 GB file**, reopened with the passphrase in 0.75 s (`backup_file_bench.tsv`; the process stood at 905 MB resident right after opening the 7 GB source store through `FhirAntDb`, before any copying, and at 728 MB after it, so the copy itself adds nothing: the raw-sqlite probe held 226 MB through the table copies). The Bundle-in-JSON path measured 51.8 s and 548 MB per 50 MB and does not reach that size. The passphrase is the cipher's own key derivation (SQLCipher-4 scheme). `restoreEncrypted` merges: the backup's resources win (their index rows and their contained rows' index rows replace the local ones), history merges, accounts and the other tables keep the local row on a key clash; a backup from an older schema is upgraded in place first, one from a newer schema is refused. `$backup` streams the file (`application/vnd.sqlite3`; `format=bundle` still gives the envelope), `$restore` takes a file body streamed to disk, a JSON envelope or a plain Bundle, told apart by the first byte; the app's backup card writes and reads the file form. **Found on the way:** on a SQLite build without the cipher, `PRAGMA key` and `ATTACH … KEY` parse and do nothing, and the first version wrote a plaintext backup and reported success (fhirant_db's own tests run on plain SQLite); `PRAGMA cipher` answers with no row there, and both directions now refuse (`NoCipherInThisBuild`). The server and app are built on sqlite3mc through their pubspec build hooks; fhirant_db's test proves the refusal, fhirant_server's the round trip.
